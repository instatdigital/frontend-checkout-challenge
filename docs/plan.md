# Frontend Checkout Challenge — Понимание проекта и план работ

## 1. Суть проекта

Тестовое задание на позицию фронтенд-разработчика. Нужно написать фронтенд магазина (каталог → корзина → оформление → оплата) на React + TypeScript поверх готового REST API. Бэкенд уже работает на Fastify, отдаёт OpenAPI-спецификацию. Фронтенд добавляется в `apps/web` как workspace `@checkout/web`.

**Ключевой критерий отбора**: DRY и обобщение кода (40 из 100 баллов). Повторяющиеся проверки HTTP-ответов, разбор тела и ошибок в компонентах — автоматически отсеивают решение. Компонент получает готовые данные или разобранную ошибку, а не сырой Response.

## 2. API-поверхность (20 операций)

### Публичные (без токена)
| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api` | Дискавери, HATEOAS-ссылки |
| POST | `/api/sessions` | Создать гостевую сессию → `{id, token, cart}` |
| GET | `/api/products` | Каталог (4 товара: lamp, mug, bag, clock) |
| GET | `/api/sandbox` | Тестовые карты + задержка оплаты |

### Защищённые (Bearer token)
| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/sessions/:id` | Информация о сессии |
| GET/PUT/DELETE | `/api/cart/items/:productId` | Корзина: прочитать/установить кол-во/удалить |
| GET | `/api/cart` | Полная корзина (items, totals, version) |
| GET | `/api/checkout/options` | Способы доставки + оплаты + корзина |
| POST | `/api/quotes` | Расчёт стоимости доставки (10 мин жизнь) |
| GET | `/api/quotes/:quoteId` | Прочитать сохранённый расчёт |
| POST | `/api/orders` | Создать заказ (нужен Idempotency-Key) |
| GET | `/api/orders` | Список заказов |
| GET | `/api/orders/:orderId` | Заказ + статус оплаты |
| GET/POST | `/api/orders/:orderId/payments` | Попытки оплаты (POST — нужна Idempotency-Key) |
| GET | `/api/payments/:paymentId` | Статус оплаты (для поллинга) |
| POST | `/api/payments/:paymentId/simulations` | Симуляция исхода карты |
| GET | `/api/payments/:paymentId/simulations/:simulationId` | Статус симуляции |

### Формат ответов
- Успех: `{ data: T, meta: { requestId }, links: { rel: { href, method } } }`
- Ошибка: `{ error: { code, message, fields? }, meta: { requestId } }`
- Все суммы — копейки (целые числа), валюта RUB

### Ключевые бизнес-правила
- Корзина версионируется; расчёт привязан к версии корзины
- Расчёт живёт 10 минут; создание заказа очищает корзину
- Idempotency-Key обязателен для POST /orders и POST /payments
- Оплата обрабатывается с задержкой (1.2 с по умолчанию) — нужен поллинг
- Одна симуляция на попытку оплаты; после decline/cancel — новая попытка с новым ключом
- clock-dot — товар с stock: 0 (недоступен)

## 4. Верхнеуровневый план работ

### Этап 0. Скаффолдинг (apps/web)
- Инициализация Vite + React + TypeScript workspace `@checkout/web`
- Настройка путей: `@/` → `src/`, интеграция с монорепо (npm workspaces)
- Базовые зависимости: react-router, стили (CSS Modules или Tailwind — на усмотрение)
- Скрипты в package.json: `dev`, `build`, `preview`
- Обновление корневого package-lock.json

### Этап 1. API-клиент (ядро DRY)
Это **самый важный** этап. Без него всё остальное не проходит критерий DRY.

**1.1. Транспортный слой** (`src/api/transport.ts`)
- Единая функция `apiRequest<T>(method, path, options?)` → `Promise<T>`
- Автоматическая инъекция `Authorization: Bearer <token>`
- Единое место для: базового URL, заголовков, сериализации тела
- Разбор ответа: проверка `response.ok`, извлечение `data` из конверта, парсинг `error` из ошибочного конверта
- Выброс типизированных ошибок (`ApiError` с `code`, `message`, `fields`)
- Поддержка `Idempotency-Key` (генерация + передача в заголовке)
- Конфликт версий (409) — отдельный тип ошибки для обработки в UI

**1.2. Типизированные эндпоинты** (`src/api/endpoints/`)
- По функции на каждый эндпоинт, делегирующей транспортному слою
- Входные и выходные типы из `@checkout/contracts` или локальные
- Сгруппировать по домену: `session.ts`, `catalog.ts`, `cart.ts`, `checkout.ts`, `orders.ts`, `payments.ts`

**1.3. Хуки** (`src/api/hooks/`)
- `useApi()` — хук для запросов: loading, data, error, refetch
- `useMutation()` — для POST/PUT/DELETE: loading, error, execute
- `usePolling()` — поллинг с интервалом, остановкой по условию и при уходе со страницы
- Все хуки возвращают разобранные данные или `ApiError` — компонент никогда не видит Response

### Этап 2. Сессия и персистенция
- `src/lib/session.ts`: создание сессии при первом визите, сохранение токена в localStorage
- Восстановление токена при перезагрузке; если токен невалиден — новая сессия
- Сохранение текущего orderId и paymentId для восстановления незавершённой оплаты

### Этап 3. Каталог
- `GET /api/products` → карточки товаров с фото-заглушками, название, цена, наличие
- Кнопка «В корзину» (недоступна при stock: 0)
- Добавление через `PUT /api/cart/items/:productId` с quantity: 1

### Этап 4. Корзина
- `GET /api/cart` → список позиций, количество, стоимость за строку и итого
- Изменение количества (input или +/-) → `PUT /api/cart/items/:id`
- Удаление → `DELETE /api/cart/items/:id`
- Пустая корзина — сообщение + ссылка в каталог
- Версия корзины — хранить для привязки к расчёту

### Этап 5. Чекаут (шаг 1: контакты + доставка)
- Форма: имя, email, телефон — валидация на клиенте
- Выбор доставки: самовывоз (выбор пункта) или курьер (ввод адреса)
- `GET /api/checkout/options` → доступные способы доставки/оплаты
- `POST /api/quotes` с `{ cartVersion, delivery }` → расчёт стоимости
- Показ: подытог, доставка, итого

### Этап 6. Чекаут (шаг 2: оплата)
- Выбор: карта или наличные
- Для карты: `GET /api/sandbox` → список тестовых карт
- Выбор тестовой карты по названию/маске (НЕ ввод номера/CVC)
- `POST /api/orders` с `{ quoteId, customer, paymentMethod }` + Idempotency-Key
- Для карты: `POST /api/orders/:orderId/payments` + Idempotency-Key
- `POST /api/payments/:paymentId/simulations` с `{ scenario: "success" | "decline" | "cancel" }`
- Поллинг `GET /api/payments/:paymentId` до терминального статуса
- При decline/cancel — новая попытка оплаты (новый Idempotency-Key)
- Защита от двойного нажатия: блокировка кнопки, идемпотентность

### Этап 7. Страница успеха
- `GET /api/orders/:orderId` → статус, состав, доставка, сумма
- Для оплаченной карты: «Заказ оплачен»
- Для наличных: «Заказ оформлен, оплата при получении»
- Статус берётся с сервера, не предполагается из факта отправки

### Этап 8. Устойчивость
- **Перезагрузка**: восстановление сессии, корзины, текущего заказа
- **Незавершённая оплата**: при восстановлении — продолжить поллинг paymentId
- **Конфликт версий корзины** (409): обновить корзину, перерассчитать
- **Устаревший расчёт**: показать предупреждение, предложить обновить
- **Ошибки API**: индикатор, кнопка «Повторить», сохранение введённых данных формы
- **Сетевые ошибки**: отличать от бизнес-ошибок API

### Этап 9. Интерфейс
- Адаптив: 1280px (десктоп) и 390px (мобильный)
- Состояния: загрузка (скелетон/spinner), ошибка, пусто
- Подписи к полям формы, навигация клавиатурой (Tab, Enter)
- Аккуратный минималистичный дизайн без макета

### Этап 10. Финализация
- README: команды запуска/сборки, архитектура API-клиента, разбор участка обработки данных
- Проверка: `npm ci && npm run dev` → всё работает
- Ручной прогон основного сценария + edge cases
- Форматирование (prettier), типы (tsc --noEmit)

## 5. Архитектурные решения (предварительные)

### Выбор инструментов
- **Сборка**: Vite (быстрый dev-сервер, простой конфиг)
- **Роутинг**: React Router v7 (SPA, каждый шаг чекаута — отдельный роут)
- **Стили**: CSS Modules + БЭМ-нейминг (нулевой runtime, изоляция, читаемость)
- **Состояние**: React Context + хуки (магазин достаточно простой, Redux избыточен)
- **Кеширование**: собственный SWR-подобный кеш (кеш по ключу, фоновое обновление, инвалидация, dedup)
- **Контракты**: `@checkout/contracts` напрямую (typebox-схемы + TS-типы)
- **Валидация форм**: собственная (минимальная, без тяжёлых библиотек)

### Принцип DRY в API-клиенте
Компонент **никогда** не делает:
- `fetch(...)` напрямую
- `response.ok` проверку
- `response.json()` парсинг
- Конверт разбора `data` / `error`

Компонент **всегда** получает:
- Готовые типизированные данные (`T`) при успехе
- Типизированную ошибку (`ApiError`) при неудаче
- Состояние загрузки (`boolean`)

Транспортный слой делает это **один раз** для всех эндпоинтов.

## 7. Риски и внимание

- **Критический порог DRY**: если хоть один компонент будет разбирать Response — решение не проходит. Весь API-обмен — только через транспортный слой.
- **Идемпотентность**: неправильная генерация/хранение ключей → дублирование заказов. Ключ привязан к действию, хранится до подтверждения результата.
- **Поллинг**: неправильная отмена → утечка запросов, подмена данных. Использовать AbortController + флаг «последний запрос побеждает».
- **Версия корзины**: при любом конфликте — перезагрузить корзину и предложить перерассчитать. Не пытаться «угадать» состояние.
- **Копейки**: везде отображать RUB, но хранить/передавать копейки. Одна функция форматирования, один проход.
