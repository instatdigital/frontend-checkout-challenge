# Конвенции проекта

## Верификация

После `write_file` или `edit` — запускать проверки по релевантности (см. «Верификация по типу файла» в секции «Процесс»).

Перед коммитом — полный цикл:

```bash
npx lefthook run pre-commit --force
```

Цепочка проверок: format → typecheck → build → lint → test (определена в `lefthook.yml`).

Если проверка падает — фиксить до перехода к следующему действию. Не пропускать, не откладывать.

Перед переходом к следующему шагу — проверить:

- Нет ли противоречий с `README.md` и `docs/ASSIGNMENT.md` (команды запуска, структура, требования)
- Получаем ли максимальную оценку по `docs/EVALUATION.md` (чеклист: `docs/evaluation-checklist.md`)

Саморефлексия после каждого шага — **действие, не ритуал**:

- Если нашли правило (что-то пошло не так, и есть вывод) → **сразу добавить в этот файл** в соответствующую секцию. Не в AI-память — в конвенции.
- Если проблема в процессе (много итераций, неочевидный порядок) → **добавить правило-ограничение** в секцию «Процесс» ниже.
- Если всё прошло ожидаемо → молча переходить к следующему шагу. Не писать «без изменений».
- Каждый найденный паттерн — с **примером** (как было → как стало), чтобы правило было конкретным.

Сверка с планом после каждого шага:

- Реализация соответствует плану → зафиксировать статус (✅) в плане
- Реализация отличается от плана → проговорить, обсудить, принять решение
- Решение уже принято ранее → обновить план, чтобы соответствовал реализации

## Размер шага

Шаг = одно моё сообщение с tool calls в ответ на запрос пользователя.

Лимит: 300 строк изменений (добавлено + изменено). Считать через:

```bash
git diff --stat HEAD -- ':!package-lock.json'
```

`package-lock.json` и автогенерированный бойлерплейт (create-vite и подобное) — не в лимите.
Планы и документация — в лимите.

Действия:

- Оценить объём до реализации. Если > 300 строк → НЕ реализовывать.
- Вместо реализации → декомпозиция в `docs/stage-N.M.md`.
- Каждый пункт декомпозиции → отдельный шаг.
- После изменений → проверить объём. При превышении → откатить лишнее.

## Порядок разработки

Сверху вниз: сначала потребитель (страница), потом зависимость (компонент).
Не должно быть неиспользуемых модулей — каждый компонент сразу интегрируется в страницу.

Шаг всегда начинается со страницы. В одном шаге:

1. Страница импортирует компонент (если > 300 строк — компонент-заглушка, реализация — следующим шагом)
2. Компонент реализуется (или заглушается)
3. Тесты

Не создавать компонент отдельным шагом без интеграции в страницу. Проверка перед созданием любого экспорта: кто его импортирует? Цепочка импортов должна дойти до файла в `pages/` или `app/`. Если импортёр — только тест или его нет → код не пишется, ждём потребителя.
Тесты потребителем не считаются.

Декомпозиция в `docs/stage-*.md` должна следовать этому правилу: шаг = страница + её зависимости, а не отдельный компонент без интеграции.

## DRY и обобщение

Компонент НЕ работает с сырым `Response`:

- Не вызывает `fetch()` напрямую
- Не проверяет `response.ok`
- Не парсит `response.json()`
- Не разбирает конверт `{data, meta, links}` / `{error, meta}`

Все API-вызовы — только через транспортный слой. Компонент получает типизированные данные
или типизированную ошибку.

## Стили

- CSS Modules: блок = `.root`, элемент = `.name`, модификатор = `.name_modifier` (файл = пространство имён)
- Импорт стилей: `import styles from './File.module.css'` (НЕ side-effect import)
- Доступ к классам: dot-нотация `styles.root`, `styles.title`, `styles.input_error`
- Компонент = папка внутри entity: `entities/product/ui/ProductCard.tsx` + `ProductCard.module.css`
- Глобальный файл — только сброс и CSS-переменные (в `app/styles/index.css`)
- Брейкпоинты: `@custom-media --desktop (min-width: 960px)` в `app/styles/breakpoints.css`, обработка через `postcss-custom-media`
- В .module.css: `@import '../../app/styles/breakpoints.css'` + `@media (--desktop) { ... }`
- Компонент и хук/тип/контекст — в разных файлах (fast refresh)
- Условные классы — через `clsx` объектный синтаксис: `clsx(styles.input, { [styles.input_error]: condition })`

## API-запросы

Типы из OpenAPI — источник истины для фронта. Генерация: `npm run gen:api -w @checkout/web`.
Endpoint-функции используют `ApiResponseData<Op, Status>` из `api-types.ts` для типов ответа.
Для типов запроса — типы из `@checkout/contracts` (шире, совместимы с формами и RHF).
Причина: OpenAPI генерирует literal-типы (`pickupPointId: 'point-center' | 'point-north'`), а RHF и формы дают `string`. Контракты (TypeBox `Static`) выводят `string`, что работает без кастов.
Файл совместимости `src/shared/api/compat-check.ts` проверяет, что типы контрактов совпадают с OpenAPI.
Если `tsc` падает на `compat-check.ts` — контракты и OpenAPI разошлись (ошибка на бэкенде).

Запрещён кастинг типов (`as Type`). Использовать аннотации (`const x: Type = value`) — TypeScript проверяет, кастинг обходит.
Не добавлять перегрузки или лишние типовые ограничения на нижних уровнях, если верхний уже гарантирует то же самое.

## Копейки

Суммы с API — копейки (целые числа). Отображение — рубли.
Одна функция форматирования, один проход.

## Идемпотентность

`Idempotency-Key` генерируется на каждое действие (создание заказа, оплата).
Хранится до подтверждения результата. При перезагрузке — восстановление по сохранённому ключу.

## Кеш

TanStack Query. Инвалидация после мутаций. Компонент не дублирует логику кеширования.
Query-ключи — фабрика в entity-слайсах: `productKeys` из `entities/product/api.ts`, `cartKeys` из `entities/cart/api.ts`.
Авторизованные запросы — `useAuthQuery` / `useAuthMutation` из `entities/session/lib/auth-hooks.ts` (токен из контекста, без `token!`).
Публичные запросы — `useApiQuery` / `useApiMutation` из `shared/api/hooks.ts`.
UI загрузки/ошибки — через `<QueryGuard>`, не через `if (isLoading)... if (error)...`.

## Формы (react-hook-form)

- `useForm` с `mode: 'onBlur'` — валидация при потере фокуса
- Использовать встроенные правила RHF: `required`, `minLength`, `maxLength`, `pattern`
- `validate` — только для проверок, которые не покрываются встроенными правилами
- Компонент формы получает `register: UseFormRegister<FormValues>` и `errors: FieldErrors<FormValues>` от родителя
- Тип формы — в странице: `type CheckoutFormValues = { customer: Customer; ... }`
- Не создавать отдельные функции-валидаторы, если RHF встроенные правила достаточны

## Тесты

TDD: сначала тест, потом реализация. Тест и реализация — в одном шаге.
Vitest. Покрытие ключевых модулей: транспортный слой, API-хуки, поллинг, сессия.
Для однотипных проверок — `it.each([{input, output}, ...])`, не писать отдельный `it` на каждый кейс.
Тесты react-hook-form: валидация асинхронна в jsdom — использовать `waitFor` после `fireEvent.blur`.

Общие хелперы — в `test/helpers/`: `createTestWrapper` (QueryClient + опц. MemoryRouter), `defaultSession` (значения для mock сессии).

### Грабли Vitest + TanStack Query

1. **`vi.mock` не работает из импортированного хелпера.** Vitest хоистит `vi.mock` только внутри самого тест-файла. Если вынести `vi.mock(...)` в `test/helpers/mock-session.ts` и импортировать — мок НЕ применится, `useSession` будет `undefined`. Поэтому `vi.mock` остаётся в каждом тест-файле, а хелпер экспортирует только данные (`defaultSession`).

2. **Тестовый wrapper должен создавать свежий `QueryClient` на каждый render.** Если создать `QueryClient` один раз в замыкании `createTestWrapper()` и переиспользовать — кеш TanStack Query протекает между тестами (данные первого теста видны во втором, `gcTime` по умолчанию 5 минут). Правильно: `new QueryClient(...)` ВНУТРИ возвращаемого компонента.

## Форматирование

Prettier: `singleQuote: true`, `printWidth: 100`, `trailingComma: "all"`.

## Shell-команды

Не использовать `cd`. Параметр `directory` в `run_shell_command` по умолчанию = корень проекта.
Нужен другой каталог → передать через `directory`.

Область действий — только файлы проекта (корень репозитория и его подкаталоги).
Не читать, не искать и не изменять файлы за пределами проекта: системные каталоги (`/c/Program Files/`, `/usr/`, `C:\Windows\` и т.д.), домашние каталоги других пользователей, глобальные конфиги.
Если нужен файл вне проекта — запросить у пользователя, не искать самостоятельно.

Не использовать `2>nul` в shell-командах — на Windows это создаёт файл `nul` вместо перенаправления в NUL device.

## FSD (Feature-Sliced Design)

Архитектура: `app → pages → features → entities → shared`. Зависимости только сверху вниз.
Проверяется ESLint (`eslint-plugin-fsd-import`): `layer-imports`, `slice-boundaries`, `public-api-imports`.

- **app/** — провайдеры, роуты, лейаут, глобальные стили
- **pages/** — страницы (слайс на роут): `pages/catalog/`, `pages/cart/`
- **features/** — пользовательские сценарии, комбинирующие entities: `add-to-cart`, `update-cart-item`
  - Кросс-доменная оркестрация (cart + session, order + payment)
  - Хуки, объединяющие несколько entities (useAuthMutation + cart API + queryClient)
- **entities/** — доменные слайсы: `product/`, `cart/`, `session/`, `checkout/`, `order/`, `payment/`
  - Каждый слайс: `api.ts`, `ui/`, `lib/`, `model/` (по необходимости), `index.ts` (публичный API)
- **shared/** — инфраструктура без бизнес-логики: `api/` (транспорт, хуки), `ui/` (QueryGuard), `lib/` (format, idempotency, query-client)

Правила:

- Импорт между слоями — только через `index.ts` (публичный API слайса)
- Entities не импортируют друг друга. Кросс-доменное взаимодействие — через features
- shared не зависит от entities (auth-hooks → entities/session, не shared)
- Алиас `@/` → `src/`. Внутри слайса — относительные импорты (`../api`, `./errors`)

## Саморефлексия: миграция на ESLint 9 + строгие правила

### Что сделано

- Миграция с oxlint на ESLint 9 (flat config)
- Добавлены: `strict` TS, React, jsx-a11y, sonarjs, `eslint-plugin-fsd-import`
- Lefthook pre-commit: format → build → lint → test
- FSD: `layer-imports`, `slice-boundaries`, `public-api-imports` — вместо скрипта `check-fsd.mjs`
- DRY: `no-restricted-syntax` (fetch вне transport), `sonarjs/no-identical-functions`, `sonarjs/no-duplicate-string`
- Resilience: `no-floating-promises`, `no-misused-promises`
- Сложность: `sonarjs/cognitive-complexity` (порог 15 по умолчанию)

### Что оказалось не так

1. **Отключение правил вместо фикса кода** — сначала несколько правил были выключены (off), хотя код можно было исправить. Пользователь указал: «Почему некоторые правила off?» и «Почему такой порог?» — правило: сначала фиксить код, off — только с обоснованием (например, `prefer-read-only-props` — React props уже readonly по контракту).
2. **Cognitive complexity** — попытка поднять порог до 20 вместо рефакторинга. Правильный подход: дефолтный порог 15, рефакторить код (выделить `restoreSession`, `initSession`, `initFresh`).
3. **ESLint 10 vs 9** — eslint-plugin-react несовместим с ESLint 10. Зафиксировать `eslint@^9`.
4. **Flat config не массив** — `react.configs.flat.recommended` и `jsxA11y.flatConfigs.recommended` — объекты, не массивы. Нельзя спредить `...`, подключать напрямую.
5. **`public-api-imports` и тесты** — тесты в `test/` не попадают в `testFilesPatterns`. Нужен override `files: ['test/**/*.test.{ts,tsx}']` с правилом `off`.
6. **`sonarjs/super-linear-regex`** — email-паттерн `/^[^\s@]+@[^\s@]+\.[^\s@]+$/` → упрощён до `/^[^\s@]+@[^\s@]+\.[^\s@]$/` (убран квантификатор `+` после последней точки).

### Правило: не ослаблять линтер

Если ESLint ругается — сначала фиксить код. Отключить правило — только если есть техническое обоснование, не «чтобы не ругалось». Каждое off-правило — с комментарием-обоснованием в конфиге.

Не менять правила ESLint самостоятельно. Если возникает конфликт (правило ругается, а фикс неочевиден) — писать, обсуждать.

## Процесс

Правила, выведенные из опыта разработки. Добавляются при саморефлексии, когда паттерн повторяется.

### Инфраструктура: целевое состояние до изменений

Перед изменением инфраструктуры (lefthook, ESLint, Vite, PostCSS, tsconfig) — описать целевое состояние в одном сообщении, а не шаг за шагом открывать проблемы.

Пример: lefthook прошёл 6 итераций (`&&` цепочка → отдельные команды → typecheck отдельно → `tsc -b` из build → parallel → откат). С целевым состоянием («5 отдельных команд, format:check, typecheck через npm-скрипт, без parallel») — 1-2 итерации.

### Memory vs конвенции

- **Конвенции (этот файл)** — правила разработки, действуют для всех агентов и сессий
- **Memory (AI-память)** — контекст проекта, предпочтения пользователя, найденные баги
- Если саморефлексия нашла правило → конвенции. Если нашли факт о проекте → memory.
- Не дублировать: правило в конвенциях → не писать в memory, и наоборот.

### Lefthook: glob по типам файлов

Команды в lefthook должны иметь узкие `glob`, чтобы doc-коммиты не запускали typecheck/build/lint/test. Lefthook пропускает команду, если ни один staged-файл не попадает в glob.

### Планирование → сразу реализация

После написания плана — сразу первый шаг реализации, не отвлекаться на сопутствующие задачи. Инфраструктура — только если блокирует реализацию.

Пример: составили план DRY-рефакторинга (6.5.1–6.5.4), но ушли в lefthook-итерации и обновление конвенций. Ни одной строчки прод-кода не написано за сессию.

### Одна тема за раз

В ходе работы всплывают смежные задачи (улучшить lefthook, обновить конвенции, почистить memory). Записать в backlog, вернуться к текущей теме.

Пример: начали с DRY → ушли в lefthook → ушли в процесс → ушли в конвенции. Каждое переключение — потеря контекста, основная задача не двигается.

Если пользователь инициирует переключение — можно переключиться. Но если всплыла «хорошая идея» по ходу — записать и продолжить текущее.

### Верификация по типу файла

После `edit`/`write_file` — запускать проверки по релевантности:

- `.md`, `.yml`, `.json` (не tsconfig) → `format:check`
- `*.{ts,tsx}` → `typecheck` + `lint`
- Полный цикл (format + typecheck + build + lint + test) → только перед коммитом

Пример: правка `docs/conventions.md` не требует typecheck. Но конвенция предписывает `npx lefthook run pre-commit --force` после каждого edit — 60с ожидания без пользы.

### Контекстное переключение: напоминание

Если разговор уходит от текущей задачи к смежной теме — напомнить: «Мы ушли от [текущая задача]. Продолжаем или записываем в backlog?»

Это касается обеих сторон: и пользователь может инициировать переключение, и агент может предложить «хорошую идею». В обоих случаях — явное решение: продолжить текущее или переключиться.

### Backlog для незапланированных задач

Файл `docs/backlog.md` — место для задач, обнаруженных в ходе работы: техдолг, новые требования, инфраструктура, процесс.

Правила:

1. Обнаружили → записали в backlog, вернулись к текущей задаче
2. При планировании нового этапа — просмотр backlog, включение релевантных пунктов в stage-документ
3. Пункт выполнен → удалить, не копить
