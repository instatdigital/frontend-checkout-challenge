# Конвенции проекта

## Верификация

После каждого вызова `write_file` или `edit` — запускать:

```bash
npm run format && npm run build -w @checkout/web && npm run lint -w @checkout/web && npm run test -w @checkout/web
```

Если проверка падает — фиксить до перехода к следующему действию. Не пропускать, не откладывать.

Перед переходом к следующему шагу — проверить:

- Нет ли противоречий с `README.md` и `docs/ASSIGNMENT.md` (команды запуска, структура, требования)
- Получаем ли максимальную оценку по `docs/EVALUATION.md` (чеклист: `docs/evaluation-checklist.md`)

Саморефлексия после каждого шага:

- Что оказалось не так, как ожидалось (ошибки, неожиданное поведение, новые ограничения)
- Что из этого требует изменений: конвенции, план, подход, зависимости
- Если всё прошло ожидаемо — явно сказать «без изменений»

Сверка с планом после каждого шага:

- Реализация соответствует плану → зафиксировать статус (✅) в плане
- Реализация отличается от плана → проговорить, обсудить, принять решение
- Решение уже принято ранее → обновить план, чтобы соответствовал реализации

## Размер шага

Шаг = одно моё сообщение с tool calls в ответ на запрос пользователя.

Лимит: 300 строк изменений (добавлено + изменено). Считать через:

```bash
git diff --stat HEAD -- ':!package-lock.json'
```

`package-lock.json` и автогенерированный бойлерплейт (create-vite и подобное) — не в лимите.
Планы и документация — в лимите.

Действия:

- Оценить объём до реализации. Если > 300 строк → НЕ реализовывать.
- Вместо реализации → декомпозиция в `docs/stage-N.M.md`.
- Каждый пункт декомпозиции → отдельный шаг.
- После изменений → проверить объём. При превышении → откатить лишнее.

## DRY и обобщение

Компонент НЕ работает с сырым `Response`:

- Не вызывает `fetch()` напрямую
- Не проверяет `response.ok`
- Не парсит `response.json()`
- Не разбирает конверт `{data, meta, links}` / `{error, meta}`

Все API-вызовы — только через транспортный слой. Компонент получает типизированные данные
или типизированную ошибку.

## Стили

- CSS Modules + БЭМ: `block__element--modifier`
- Компонент = папка: `components/ProductCard/ProductCard.tsx` + `ProductCard.module.css`
- Глобальный файл — только сброс и CSS-переменные

## Копейки

Суммы с API — копейки (целые числа). Отображение — рубли.
Одна функция форматирования, один проход.

## Идемпотентность

`Idempotency-Key` генерируется на каждое действие (создание заказа, оплата).
Хранится до подтверждения результата. При перезагрузке — восстановление по сохранённому ключу.

## Кеш

TanStack Query. Инвалидация после мутаций. Компонент не дублирует логику кеширования.

## Тесты

TDD: сначала тест, потом реализация. Тест и реализация — в одном шаге.
Vitest. Покрытие ключевых модулей: транспортный слой, API-хуки, поллинг, сессия.

## Форматирование

Prettier: `singleQuote: true`, `printWidth: 100`, `trailingComma: "all"`.

## Shell-команды

Не использовать `cd`. Параметр `directory` в `run_shell_command` по умолчанию = корень проекта.
Нужен другой каталог → передать через `directory`.
