# Конвенции проекта

## Верификация

После каждого вызова `write_file` или `edit` — запускать:

```bash
npx lefthook run pre-commit --force
```

Цепочка проверок: format → build → lint → test (определена в `lefthook.yml`).

Если проверка падает — фиксить до перехода к следующему действию. Не пропускать, не откладывать.

Перед переходом к следующему шагу — проверить:

- Нет ли противоречий с `README.md` и `docs/ASSIGNMENT.md` (команды запуска, структура, требования)
- Получаем ли максимальную оценку по `docs/EVALUATION.md` (чеклист: `docs/evaluation-checklist.md`)

Саморефлексия после каждого шага:

- Что оказалось не так, как ожидалось (ошибки, неожиданное поведение, новые ограничения)
- Что из этого требует изменений: конвенции, план, подход, зависимости
- Если всё прошло ожидаемо — явно сказать «без изменений»
- **Найденные правила — сохранять в этот файл**, не в AI-память

Сверка с планом после каждого шага:

- Реализация соответствует плану → зафиксировать статус (✅) в плане
- Реализация отличается от плана → проговорить, обсудить, принять решение
- Решение уже принято ранее → обновить план, чтобы соответствовал реализации

## Размер шага

Шаг = одно моё сообщение с tool calls в ответ на запрос пользователя.

Лимит: 300 строк изменений (добавлено + изменено). Считать через:

```bash
git diff --stat HEAD -- ':!package-lock.json'
```

`package-lock.json` и автогенерированный бойлерплейт (create-vite и подобное) — не в лимите.
Планы и документация — в лимите.

Действия:

- Оценить объём до реализации. Если > 300 строк → НЕ реализовывать.
- Вместо реализации → декомпозиция в `docs/stage-N.M.md`.
- Каждый пункт декомпозиции → отдельный шаг.
- После изменений → проверить объём. При превышении → откатить лишнее.

## Порядок разработки

Сверху вниз: сначала потребитель (страница), потом зависимость (компонент).
Не должно быть неиспользуемых модулей — каждый компонент сразу интегрируется в страницу.

Если страница + компонент + тесты + стили ≤ 300 строк → всё в одном шаге.
Если > 300 строк → в шаге страницы создаём компонент-заглушку, реализацию — следующим шагом.

Не должно быть «пустых» сущностей. Перед созданием любого экспорта (компонент, хук, ключ,
эндпоинт) — проверить: кто его импортирует? Цепочка импортов должна дойти до файла в `pages/`
или `app/`. Если импортёр — только тест или его нет → код не пишется, ждём потребителя.
Тесты потребителем не считаются.

## DRY и обобщение

Компонент НЕ работает с сырым `Response`:

- Не вызывает `fetch()` напрямую
- Не проверяет `response.ok`
- Не парсит `response.json()`
- Не разбирает конверт `{data, meta, links}` / `{error, meta}`

Все API-вызовы — только через транспортный слой. Компонент получает типизированные данные
или типизированную ошибку.

## Стили

- CSS Modules + БЭМ: `block__element--modifier`
- Компонент = папка внутри entity: `entities/product/ui/ProductCard.tsx` + `ProductCard.module.css`
- Глобальный файл — только сброс и CSS-переменные (в `app/styles/index.css`)
- Компонент и хук/тип/контекст — в разных файлах (fast refresh)
- Условные классы — через `clsx` объектный синтаксис: `clsx('block__element', { 'block__element--modifier': condition })`

## API-запросы

Типы из OpenAPI — источник истины для фронта. Генерация: `npm run gen:api -w @checkout/web`.
Endpoint-функции используют `ApiResponseData<Op, Status>` и `ApiRequestBody<Op>` из `api-types.ts`.
Файл совместимости `src/shared/api/compat-check.ts` проверяет, что типы контрактов совпадают с OpenAPI.
Если `tsc` падает на `compat-check.ts` — контракты и OpenAPI разошлись (ошибка на бэкенде).

Запрещён кастинг типов (`as Type`). Использовать аннотации (`const x: Type = value`) — TypeScript проверяет, кастинг обходит.
Не добавлять перегрузки или лишние типовые ограничения на нижних уровнях, если верхний уже гарантирует то же самое.

## Копейки

Суммы с API — копейки (целые числа). Отображение — рубли.
Одна функция форматирования, один проход.

## Идемпотентность

`Idempotency-Key` генерируется на каждое действие (создание заказа, оплата).
Хранится до подтверждения результата. При перезагрузке — восстановление по сохранённому ключу.

## Кеш

TanStack Query. Инвалидация после мутаций. Компонент не дублирует логику кеширования.
Query-ключи — фабрика в entity-слайсах: `productKeys` из `entities/product/api.ts`, `cartKeys` из `entities/cart/api.ts`.
Авторизованные запросы — `useAuthQuery` / `useAuthMutation` из `entities/session/lib/auth-hooks.ts` (токен из контекста, без `token!`).
Публичные запросы — `useApiQuery` / `useApiMutation` из `shared/api/hooks.ts`.
UI загрузки/ошибки — через `<QueryGuard>`, не через `if (isLoading)... if (error)...`.

## Формы (react-hook-form)

- `useForm` с `mode: 'onBlur'` — валидация при потере фокуса
- Использовать встроенные правила RHF: `required`, `minLength`, `maxLength`, `pattern`
- `validate` — только для проверок, которые не покрываются встроенными правилами
- Компонент формы получает `register: UseFormRegister<FormValues>` и `errors: FieldErrors<FormValues>` от родителя
- Тип формы — в странице: `type CheckoutFormValues = { customer: Customer; ... }`
- Не создавать отдельные функции-валидаторы, если RHF встроенные правила достаточны

## Тесты

TDD: сначала тест, потом реализация. Тест и реализация — в одном шаге.
Vitest. Покрытие ключевых модулей: транспортный слой, API-хуки, поллинг, сессия.
Для однотипных проверок — `it.each([{input, output}, ...])`, не писать отдельный `it` на каждый кейс.
Тесты react-hook-form: валидация асинхронна в jsdom — использовать `waitFor` после `fireEvent.blur`.

## Форматирование

Prettier: `singleQuote: true`, `printWidth: 100`, `trailingComma: "all"`.

## Shell-команды

Не использовать `cd`. Параметр `directory` в `run_shell_command` по умолчанию = корень проекта.
Нужен другой каталог → передать через `directory`.

## FSD (Feature-Sliced Design)

Архитектура: `app → pages → entities → shared`. Зависимости только сверху вниз.
Проверяется ESLint (`eslint-plugin-fsd-import`): `layer-imports`, `slice-boundaries`, `public-api-imports`.

- **app/** — провайдеры, роуты, лейаут, глобальные стили
- **pages/** — страницы (слайс на роут): `pages/catalog/`, `pages/cart/`
- **entities/** — доменные слайсы: `product/`, `cart/`, `session/`, `checkout/`, `order/`, `payment/`
  - Каждый слайс: `api.ts`, `ui/`, `lib/`, `model/` (по необходимости), `index.ts` (публичный API)
- **shared/** — инфраструктура без бизнес-логики: `api/` (транспорт, хуки), `ui/` (QueryGuard), `lib/` (format, idempotency, query-client)

Правила:

- Импорт между слоями — только через `index.ts` (публичный API слайса)
- Entities не импортируют друг друга. Кросс-доменное взаимодействие — через pages
- shared не зависит от entities (auth-hooks → entities/session, не shared)
- Алиас `@/` → `src/`. Внутри слайса — относительные импорты (`../api`, `./errors`)

## Саморефлексия: миграция на ESLint 9 + строгие правила

### Что сделано

- Миграция с oxlint на ESLint 9 (flat config)
- Добавлены: `strict` TS, React, jsx-a11y, sonarjs, `eslint-plugin-fsd-import`
- Lefthook pre-commit: format → build → lint → test
- FSD: `layer-imports`, `slice-boundaries`, `public-api-imports` — вместо скрипта `check-fsd.mjs`
- DRY: `no-restricted-syntax` (fetch вне transport), `sonarjs/no-identical-functions`, `sonarjs/no-duplicate-string`
- Resilience: `no-floating-promises`, `no-misused-promises`
- Сложность: `sonarjs/cognitive-complexity` (порог 15 по умолчанию)

### Что оказалось не так

1. **Отключение правил вместо фикса кода** — сначала несколько правил были выключены (off), хотя код можно было исправить. Пользователь указал: «Почему некоторые правила off?» и «Почему такой порог?» — правило: сначала фиксить код, off — только с обоснованием (например, `prefer-read-only-props` — React props уже readonly по контракту).
2. **Cognitive complexity** — попытка поднять порог до 20 вместо рефакторинга. Правильный подход: дефолтный порог 15, рефакторить код (выделить `restoreSession`, `initSession`, `initFresh`).
3. **ESLint 10 vs 9** — eslint-plugin-react несовместим с ESLint 10. Зафиксировать `eslint@^9`.
4. **Flat config не массив** — `react.configs.flat.recommended` и `jsxA11y.flatConfigs.recommended` — объекты, не массивы. Нельзя спредить `...`, подключать напрямую.
5. **`public-api-imports` и тесты** — тесты в `test/` не попадают в `testFilesPatterns`. Нужен override `files: ['test/**/*.test.{ts,tsx}']` с правилом `off`.
6. **`sonarjs/super-linear-regex`** — email-паттерн `/^[^\s@]+@[^\s@]+\.[^\s@]+$/` → упрощён до `/^[^\s@]+@[^\s@]+\.[^\s@]$/` (убран квантификатор `+` после последней точки).

### Правило: не ослаблять линтер

Если ESLint ругается — сначала фиксить код. Отключить правило — только если есть техническое обоснование, не «чтобы не ругалось». Каждое off-правило — с комментарием-обоснованием в конфиге.
